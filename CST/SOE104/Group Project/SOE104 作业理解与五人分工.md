# SOE104 作业最新理解与五人分工

> 本页基于官方三份文档（Tasksheet / Engine Rules / API Reference）+ ChatGPT 最新梳理，重点讲**新理解**：我们只需要写"决策部分"、全回合调用时序、五人工作量均分方案。规则细节参见 [[SOE104 第一次小组会议_项目概要]]。

## 一、作业内核（一句话）

**用 Java 面向对象写一支会自己决策的探险队（3–5 名成员），120 回合内从 0 走到 2000 英里，尽量全员存活并保留物资。** 引擎（老师平台）负责跑游戏、结算事件和评分；我们只负责队伍"怎么决策"。

- 交付：Java 源码 / 源码 ZIP（**不需要写报告**）；截止 **2026-12-13 23:59（北京时间）**；无限次提交，**按最后一次提交计分**。
- 每回合要回答三个问题：
  1. **全队怎么走、怎么吃**——选速度和口粮，平衡进度、健康、消耗；
  2. **遇到事件怎么办**——9 种事件 × 稳妥 SAFE / 冒险 RISKY / 回避 AVOID；
  3. **每名成员做什么**——打猎 / 治疗 / 休息 / 探路 / 推进 / 防守，避免重复和浪费。

## 二、重要澄清：我们只需要写决策部分

**不需要修改或实现游戏引擎**：我们看不到引擎源码，提交的代码由平台调用和执行。可以理解为：老师提供"游戏世界与规则"，我们实现"队伍的大脑"。

| 部分 | 我们要做什么 | 是否必须 |
|---|---|---|
| `PartyFactory` | 创建并组装队伍，返回 3–5 名游戏成员 | ✅ 必须（且只能有一个实现） |
| 成员类 `act()` | 继承官方角色类，决定该成员本回合的行动 | ✅ 必须 |
| `buySupplies()` | 决定出发采购清单 | 可选（不写 = 默认采购） |
| `PartyStrategy.decide()` | 决定全队行进速度和口粮 | 可选（不写 = 默认 NORMAL/FULL） |
| `Resolver.resolve()` | 决定事件应对与交易行为 | 可选（不写 = 永远 SAFE） |

> 我们返回"打猎"这个动作，引擎负责扣弹药、加食物——**结算逻辑一行都不用写**。后三项接口上可选，但为了成绩建议全部实现。

## 三、全回合流程图（先看这张图）

![[SOE104 游戏流程全图.png]]

最容易混淆的三点：

1. **先吃饭，后打猎**：本回合吃饭时已经缺粮，之后的打猎救不了这次饥饿 → 必须提前备粮。
2. **成员行动发生在事件结算之后**：能对已发生的事件作反应，但不能阻止事件伤害。
3. **牛为 0 不会立即结束游戏**：马车基础行进停止，但吃饭和成员行动照常。

> 🔧 **更正（相比初版概要）**：MOVE 是**执行者自己 −1 血**，不是全队掉血——三份官方 PDF 对此一致。

## 六、五人分工（总工作量大致各 20%）

> 现实组员 ≠ 游戏职业：队伍允许 3–5 人、职业可重复，按效果选择。

| 组员 / 工作包 | 具体负责什么 | 需要掌握的东西 | 交付与验收 | 工作量平衡 |
|---|---|---|---|---|
| **A：架构、入口与集成** | 唯一的 `PartyFactory`；组装成员、策略和事件处理器；设计共享上下文；统一接口与命名；负责合并、编译、打包 | Java 接口、构造器、组合、封装、对象引用；API 调用顺序；JDK 21、Git 基础 | 可运行骨架；共享上下文读写约定；合并后的提交包。验收：恰好一个工厂、3–5 名成员、平台能编译运行 | 策略较少，补上持续集成、接口协调、提交检查 |
| **B：行进与全队策略** | `PartyStrategy.decide()`：按健康、食物、牛数、剩余路程决定速度与口粮；实现推进类角色（Scout、Driver） | 条件分支、枚举、接口实现；消耗估算；速度-健康权衡；角色继承/重写 | 全队决策规则表；策略实现；推进角色；不同速度口粮组合的回放对比。验收：能解释每种切换条件及效果 | 核心策略，但只承担推进相关角色 |
| **C：补给经济与狩猎** | 出发采购清单；Hunter 行为；食物可维持回合数、弹药需求、容量余量；向 E 提供交易补给需求 | 资源预算、整数运算、阈值判断；集合与采购列表；继承、多态；打猎收益与资源上限 | 采购方案及预算；Hunter 实现；食物/弹药预警。验收：避免食物溢出浪费、能解释饥饿或弹药耗尽原因 | 采购较简单，补上食物经济分析、狩猎协调与参数实验 |
| **D：生存、行动协调与效果评估** | Doctor 行为；治疗、自保、防守优先级；共享上下文避免多人重复 DEFEND；整理三种种子回放、对比改动前后效果 | 健康状态判断；成员行动顺序；共享状态重置更新；边界情况；实验记录 | 治疗与防守协调规则；Doctor 实现；回放对比与问题清单。验收：无重复防守/无效治疗、能定位死亡原因 | 角色代码较少，补上跨成员协调和实验分析 |
| **E：事件处理与交易** | `Resolver.resolve()`：覆盖 9 种事件；按严重度和资源选 SAFE/RISKY/AVOID；交易站买卖与砍价；Mechanic 行为 | 接口、枚举/事件分支；概率与风险比较；市场价格与限制；共享上下文 vs 库存快照 | 9 种事件决策表；Resolver 和交易逻辑；角色行为。验收：所有事件都有处理、缺钱缺物资有退路、每次市场只做一笔交易 | 事件分支和交易较多，角色部分精简 |

> 这是**工作量估算，不是评分比例**。第一轮跑通后再调整一次：若 E 的交易逻辑超量，可把交易需求计算交给 C；若 A 联调压力偏大，各模块先自验再合并。

## 七、五个人必须先统一的协作规则

**调用时序（最关键）：全队策略 → 行进 → 吃饭 → 事件处理 → 成员按名单顺序行动。**

- **打猎发生在吃饭之后**：当回合吃饭前已缺粮，不能指望稍后的打猎补救这次饥饿。
- `Resolver` 收到的事件对象**没有完整库存视图**，必须通过共享上下文与策略模块协调；策略记录的是较早时点信息，不能当成实时库存。
- **DEFEND 每回合最多生效一次**：必须约定由谁防守，其他成员继续做有价值的事。
- 共享上下文先约定"**谁写、谁读、何时重置**"，避免五个人各自维护一套互相矛盾的状态。

**第一次会议先定五件事**：游戏队伍配置、共享上下文字段、模块接口、行动优先级、统一提交负责人。

## 八、推荐推进顺序

1. **先跑通基线**：从官方 sample 入手，把工厂、成员、策略、事件串起来，尽早拿到第一次平台回放。
2. **解决主要失败原因**：优先检查饥饿、死亡、牛损失、进度不足；每次只调整少数变量，记录效果。
3. **再优化得分**：对比三个种子的表现，改进采购、治疗、事件和市场选择；同时检查 OOP、命名、效率。
4. **最后统一提交**：最多 20 个 .java 文件、无 package 声明、ZIP 根目录放源码。**评分取最后一次提交，不是历史最高分。**
